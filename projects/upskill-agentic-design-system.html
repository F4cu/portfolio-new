UpSkill Agentic Design System

This is the second chapter of UpSkill. Part 1 designed the foundations; Part 2 turns them into a working system in code, where AI agents operate under the same governance as everything else: machine-readable, checked by scripts and humans, and built to run inside a fixed AI usage budget.

Part 1: UpSkill Design Foundations

Role

Senior Product Designer

Main Goal

Agentic design system

Challenge

Trustworthy AI output at solo scale

LLMs generating UI without a machine-readable system fabricate token names, drift from brand, and lose context between sessions. A design system only constrains AI output if the AI can actually read it: prose documentation does not stop a model from inventing a plausible-sounding token or reaching for a component that was never built. Every layer here (tokens, components, layout, governance) is written as data a machine can parse and a script can check, while staying readable for people.

The personal constraint is just as real. One person maintains the whole system: the token pipeline, 27 components, documentation, and governance, on a consumer AI plan with one shared usage window. Every agent workflow draws from the same budget; there is no team to split the work across and no API invoices to absorb a wasteful architecture.

Objectives

  • Make every part of the system readable by machines as well as people
  • Keep AI involvement governed: agents propose, checks and humans decide
  • Fit all automation inside a fixed, shared LLM usage budget
  • Support two brands, two themes, and three breakpoints from one token source
The Contract

Components as data, not prose

Every one of the 27 components ships a JSON metadata file instead of a Markdown usage page: purpose, variants, states, accessibility contract, composition rules, and anti-patterns, validated in CI against a JSON Schema on every pull request. Docs rot; contracts do not, because nothing forces a Markdown page to stay in sync with the code it describes, but a schema failure blocks the merge.

The validator goes further than shape-checking. It merges every token source file into one tree and confirms every token path a component claims to use actually resolves to a real value, so a component cannot claim a token that got renamed: the check fails at the pull request that introduced the drift, not months later. When a review finds a real gap, a missing ARIA attribute, a misuse pattern, the fix routes back into the specific metadata field it belongs to, so the next scaffold, layout, or reviewer inherits it as a checked fact, not a story someone has to remember.

The same principle repeats one level up in layout. A fixed semantic hierarchy, Page, Header, Section, Container, Column, Component, Footer, maps onto sanctioned HTML landmarks, so a generated layout has one structurally correct shape instead of being re-derived from the brief each run. A validation script enforces it deterministically: exactly one main landmark, every section named, every extra nav uniquely labelled, a script's judgment, not a reviewer's attention.

The Loop

A verified path from scaffold to PR

The verified component loop runs the same path every time: sense the current pipeline state, scaffold from schema and Figma context, deterministic gates check metadata, types, the build, and accessibility, a human approves a visual checkpoint, a fresh, read-only adversarial subagent reviews the diff, and only then does a pull request open. AI does the labor of drafting and iterating; scripts and humans hold every gate that decides whether the result ships.

The reviewer's independence is structural, not requested. It is a subagent that starts cold, reads only the diff and a frozen snapshot, and is read-only by tool grant, no edit access at all, so "reviewer reports, main session decides" cannot be skipped under time pressure. This is one of nine developer-triggered agentic moments; nothing in the system runs continuously.

It Learns

Self-improving feedback

Findings do not die with the pull request that found them. They route to a durable home: an ARIA gap updates the component's metadata, a misuse pattern becomes a new anti-pattern entry, a token convention question goes to the token-authoring rules, a contrast miss goes to a curated, reviewed pairing list. A problem found once is a checked fact every future scaffold, layout, and reviewer inherits, never rediscovered from scratch.

The run-ledger is the receipts drawer. It is append-only, committed, and now old enough to read. The adversarial reviewer earned its cost on every interactive and composite component it reviewed, and found nothing beyond the gate on the layout primitives, a routing heuristic the ledger surfaced on its own, not a hunch. No run needed a manual rescue. The system is explicit about scope: the ledger covers only the full-review path, so the claim is measured where it matters most and honestly unmeasured for the rest.

Ledgers are designed to shrink to zero, not just shrink. New entries are structurally forbidden on both tracked lists: a new interactive component cannot be waived onto the accessibility-test backlog, a new contrast failure cannot be waived at all, only routed into the curated pairing list. The accessibility backlog has already reached the state it was built to reach: an empty, checked-in list.

The docs get the same treatment. CI detects when a doc has gone stale against the source files it depends on; rewriting is developer-triggered and touches only stale sections. Before the pull request, a fresh, read-only docs-scribe critic, with no memory of the rewrite session, reviews the new prose against the glossary for three audiences (product manager, designer, engineer), checking that every technical term is grounded, not just present. It is the same adversarial shape as component review, applied to documentation instead of code.

Foundations

Foundations in brief

Four-layer token pipeline. Primitives, brand, theme, and device, each layer only able to reference the one before it, with one Style Dictionary build as the sole bridge into anything a component can consume; components never import source JSON. That chokepoint is what makes 2 brands x 2 themes x 3 breakpoints resolve from a single source without per-component special-casing.

Context economics as an architecture constraint. Agents read frozen, committed snapshots (Airtable governance, Figma variables, token usage, component patterns), never live APIs. The always-loaded instruction file is capped and CI-enforced at 200 lines. A parallel agent-swarm blueprint was evaluated and rejected: on a shared usage window, parallel workers drain the same budget faster without improving the outcome, so a sequential, at-most-two-agent loop shipped instead.

Measured, not assumed. A cross-component pattern-context harness looked like a pure improvement, more structural context fed into every generation task. Measured against seven pre-registered tasks, it improved composition and layout work but measurably worsened component scaffolds. It shipped only where it measured well: into layout generation, never into scaffolding.

Governance

Governance and observability

  • Airtable, per-column ownership. Human judgment (deprecation decisions, done/todo sign-off) is authored directly in Airtable and pulled into code; derived state (pipeline stage, maturity) is pushed from code on merge. The two never share a column.
  • The "don't downgrade done" guard. A sync never overwrites a human-set done or todo value, enforced as a check in the sync script, not a policy someone has to remember.
  • ADRs amended or superseded, never silently rewritten. A wrong decision and the reasoning that corrected it both stay on the record.
  • The CLI is the frozen state, rendered. npm run status, status:board, and status:component are simple renderers over the same committed files an agent reads mid-loop, no Airtable tab, no Figma tab, no agent session needed to answer where everything stands.

Impact

What it changes for each audience

Compared to a standard design system with little automation:

  • Developer, consumer of the components. Inherits a trustworthy contract without reading the implementation: components only ever consume built tokens, the component set is a real, finite ceiling, and generated layouts follow one grammar instead of per-page improvisation. AI output against this system is checked, not trusted.
  • Designer. Trades the "tweak the variable in Figma" workflow for a single, versioned, diffable source of truth that never drifts silently; a value changed once propagates to every brand, theme, and breakpoint, and Figma stays an honest design surface instead of a hidden second source of truth.
  • Product owner, maintainer. Governance without meetings: deprecations, reversals, and quality gates are on the record and enforced by CI, deterministic checks absorb the boring majority of review so judgment is spent only where it is genuinely ambiguous, and the whole thing runs inside one consumer AI budget.

The numbers

Each measured against the repo's own CI gates, ledgers, or harness results, not asserted:

  • 27 production components, each shipping schema-validated metadata, stories, and accessibility coverage
  • 2 brands x 2 themes x 3 breakpoints resolved from one token source
  • 12 of 12 full-loop runs passed the deterministic gate, and the adversarial reviewer still found issues beyond the gate in 7 of 12 runs (18 findings total)
  • Pattern-context harness: 13% fewer rule violations overall, shipped only into the task types where it measured positive
  • Accessibility backlog empty, with contrast checked mathematically in CI over the built CSS
  • 20 ADRs, every reversal amended or superseded in the open

None of this required a systems team: governance, quality, and multi-brand consistency held because the system itself is machine-readable and checks its own work.
