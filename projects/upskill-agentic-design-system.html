UpSkill Agentic Design System

This is the second chapter of UpSkill. Building a full coded component library that uses AI as infrastructure: machine-readable, stable for LLMs, and token-efficient.

UpSkill Design Foundations

Role

Senior Product Designer

Main Goal

Agentic design system

Challenge

Governing a design system with AI, reliably, on a solo budget

AI can generate UI faster than anyone can review it, and it can do that trustworthily only against a system it can actually read. Most AI-paired systems reach for expensive patterns instead: agent swarms, live API calls, stacked MCP connections.

It also has to be reliable. An agent that generates a component should land on a consistent, verifiable result rather than a different one each run.

And it has to stay legible to one person. The maintainer sees the whole system, and the system keeps a readable account of its own status.

Approach

A pipeline the agent can read and a person can see whole

What we discarded

Three early bets were dropped before the system took shape. Figma as the token source was reversed once its Variables API proved Enterprise-only, so code became the source and Figma a downstream mirror. A parallel agent swarm was cut once it was clear that on a solo Claude Pro plan parallel workers drain a single usage window many times faster. And live MCP connections were ruled out for the day-to-day pipeline, kept only for one-off interactive work.

What these share is a budget: one person, one usage window, no Enterprise tier. Each rejection removed an expensive or non-deterministic dependency, and everything that remained had to earn its place by being cheap and legible.

Foundation

One fact shapes the whole system: an agent's output changes from run to run, so everything it reads is pinned down in advance as machine-readable files a script can validate, not code it has to interpret. A few structural choices make that possible. See the structural choices

  • A metadata schema for components and layout. Each component ships a schema-validated contract covering variants, states, tokens, accessibility, and composition, and its token paths are checked against the real built output. Scaffold and layout agents read and cite that contract instead of inferring intent from code.
  • A fixed component set. A small, closed list where a three-question test gates every addition, so agents compose from known parts rather than inventing new ones.
  • Four-layer tokens. Every value resolves through primitives → brand → theme → device, with later layers overriding earlier ones. Components consume the built output, never the source.
  • A deterministic split. Most of the system is plumbing. GitHub Actions, npm scripts, and direct REST calls move state between tokens, components, Airtable, and CI, with no model in the loop. Only the few jobs a script genuinely cannot do, such as generating a component or reviewing it, are handled by one of nine specific Claude commands.

Stabilize the input

The pipeline runs in one direction and passes files, not calls. A single sensing script, npm run sense, aggregates component state, review status, and governance into snapshots, and those files are all the agents ever read. Because a maintainer's status check and an agent's scaffold read the identical file, every run starts from the same ground a live API could never guarantee.

Figma and Airtable are downstream mirrors of the code tokens, not sources of them. Maintenance loops refresh those mirrors from the codebase, so the source stays single while the surfaces designers and stakeholders use stay current.

The loops

Generation is bounded before it begins. /add-component runs in a fixed order — sense → scaffold → gate → review → PR — where a deterministic gate (typecheck, build, lint, a11y) must pass before a fresh-context agent reviews the result adversarially. Layout generation composes from the same fixed set, each structural choice citing a metadata rule. The schema, fixed set, and grammar narrow what the agent can produce, and nothing agent-written reaches main unreviewed.

The system turns its own mistakes into structure. /extract-learnings routes each review finding to a durable home — a component's metadata, a token convention, or the curated contrast-pair list — so the next agent reads the lesson directly instead of rediscovering the bug.

It also documents itself. A staleness check flags drifted pages and /docs-sync rewrites only the stale sections, each rewrite checked by a read-only subagent for first-read clarity before a PR opens.

Governance and observability

Airtable is the governance layer for components and tokens. Every component carries status on two axes — maturity (beta or production-ready), pushed automatically from the code, and implementation (is the build finished), set by hand — kept in separate columns so a human's done always wins and the automated push can never overwrite it.

A maintainer can read the same committed snapshots from a small CLI (npm run status, status:board, status:component <Name>) with no live API call and no model in the loop, seeing exactly what the last agent saw without leaving the editor.

Solution

AI as infrastructure, not assistant

The result is a design system an agent can trust without guessing, and one person can still see whole. Every token, component, and layout choice is machine-readable and schema-checked, so agents read facts instead of inferring them from code, and each addition clears a deterministic gate and a human-reviewed PR before it ships.

What changed is the role AI plays. Rather than sitting on top as an assistant, it runs as infrastructure inside the pipeline — bounded, sequential, limited to the jobs a script cannot do. Everything checkable stays deterministic, so output is reliable instead of varying from run to run.

For the organization, it gives one person a team's rigor. The maintainer sees the whole system from the command line, the system documents and corrects itself as it grows, and governance usually reserved for larger teams arrives on a solo budget.

Impact

Impact

  • Lower cost. 22 scripts, 37 npm commands, and 7 GitHub Actions run with zero LLM or MCP calls. Agents handle only the 9 Claude commands reserved for jobs a script cannot do, so there is no per-run model spend or vendor lock-in on the day-to-day pipeline. (Measured)
  • Reliable visibility. Committed snapshots replace live API reads at 20 points across 7 commands. For Airtable, a 977-byte snapshot stands in for a 60,695-byte response, a 62× reduction (measured 2026-07-23). A maintainer checks status in one command and reads the same result every time. (Measured)
  • Higher-quality output. Across /add-component runs the deterministic gate passed 12 of 12, and adversarial review caught extra findings in 7 of 12 before a human saw the PR, so reviewers spend their time on judgment rather than catching regressions. (Measured)
  • Accessibility by default. Lint on every commit, plus coverage and behavioral tests before merge, means designers and developers inherit accessible components rather than auditing them after the fact.
