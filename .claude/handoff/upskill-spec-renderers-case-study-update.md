## What the case study proves today

Strong evidence of **building governance and tooling**: deterministic scripts, layered memory, nine agent commands, guards, and five measured outcomes (9/9 clean builds, 2.4× Figma accuracy, zero model spend on routine work, 20 API calls replaced by snapshots, guided governance on 10 of 11 decisions), all backed by hidden-answer-key rigor.

Gaps a product designer / design systems recruiter will notice:

1. **No readable docs.** The contracts (`metadata.json`, `spec.json`) are described but never shown as guidance a designer or engineer would read.
2. **Little visible design craft.** No anatomy, usage guidance or don'ts on the page.
3. **No sign of working where designers work.** All Figma work goes through third-party CLI or MCP. You haven't built any Figma tooling of your own.

## What each part of the work would prove

### Part A: generated Usage / Spec / Accessibility pages
- **Documentation, a core DS deliverable,** with a page split chosen deliberately from Carbon, M3 and Primer conventions.
- **"The docs are the contract."** The file that gates code review and steers agents also renders the public guidelines, so the pages can't drift away from the component. This is the strongest point because it ties the agentic story to a problem every DS team has.
- **Content design.** Hand-written usage guidance, anti-patterns with reasons and alternatives, and variant purposes show judgment, not just plumbing.
- **Accessibility as its own tab.** Signals DS maturity.
- **A public URL a recruiter can click.** No Figma access or repo reading needed. That fixes the page's biggest weakness: right now everything is described and nothing is browsable.

### Part B: Figma parity plugin
- **Figma Plugin API depth** (variables, `boundVariables`, component properties). Also closes the "custom design-system tooling" gap in `~/projects/ds-jobs/profile/index.md` §5.
- **Clear positioning against known tools.** Code Connect answers "what code do I write?" and EightShapes Specs / Spectacular answer "what is this made of?". This plugin answers "does Figma still match the code?"
- **Known-answer test.** Predicting which traced drift items get flagged before the run continues the hidden-answer-key rigor, the most credible thread in the case study.

### Decisions and `ruledOut[]` as agent memory
- **Design rationale as an artifact.** "We considered X and rejected it, here's why" is what senior DS people care about. If the reviewer stops re-proposing rejected options, craft connects back to the AI story.

## Rules for the update

- **Only claim what shipped.** "Built" until measured; numbers only from `08-measured-impact.md`.
- **For product designer roles, Part A carries most of the value.** Part B mostly appeals to DS engineering and tooling roles. If only Part A ships, still update the page.
- **Framing:**
  - Never call Part A "autogenerated docs" (sounds like low-value API output). Say: guidance written once as structured data, with pages that can't drift.
  - Never call Part B a spec-sheet generator (reads as a copy of EightShapes Specs). Lead with the parity check.
- **Measurements that turn it into impact, not scope:**
  - Time to hand-document Button vs. generating it.
  - Share of rendered rows that trace to a spec or metadata field.
  - Phase B2 known-answer result: traced items flagged or missed, plus new findings.
  - Ruled-out re-proposal count before/after, from `run-ledger.json`.
- **One-line positioning shift:** from "built a clever AI harness" to "built a design system people can read and trust, and an AI harness that keeps it honest."
